## P1 lane rules

These rules add to the lane rules in EXECUTION.md.

1. **Ports and data dirs.** Task P1-n uses port `18180 + n` and `../shelfy-web-local/data/p1-<n>`, so P1 lanes never collide with P0 lanes.
2. **Generated artifacts.** Only a lane that changes the HTTP API regenerates `openapi.json` and the TS client. After a rebase, regenerate them; never merge them by hand. No wave pairs two such lanes.
3. **Shared registries are owned files.** These files may be touched only by tasks that list them under "Owns":
   - the router composition, the admin CLI dispatch and the job-kind registry;
   - each crate's `lib.rs`, `Cargo.toml` and `Cargo.lock`;
   - `.github/workflows/ci.yml`, `package.json` and `pnpm-lock.yaml`.
4. **Authz per route.** Every new route ships three tests: 401 without auth, 404 for another user's resource, and a bearer token refused on cookie-only routes. The generated authz matrix stays in P5 (G8).
5. **Desktop renderer.** TS tasks may edit the `src/` files they list; this is an explicit exception to D25.
   - `pnpm run lint`, `typecheck`, `test:run` and `pnpm test:e2e` stay green.
   - No `electron/` changes. A seam operation with no desktop IPC is turned off by capability.
6. **Test data.**
   - Perf and e2e tests use `admin synth` libraries (from P1-05). Before P1-05, use a mock client or a fixture DB.
   - The reference library is used only for local dry runs that print aggregate counts (lane rule 9).
7. **VPS work (E2).**
   - The lead runs it.
   - Record Hermes health before and after: container healthy, probe up, limits unchanged. Never touch the Hermes service.
   - Deploy the integration tip as a new `server-v0.1.0-rc.N`.
8. **No owner session in automation.**
   - Live checks use `admin bench`, metrics and unauthenticated routes.
   - Anything that needs a signed-in browser on the live host is an owner step.
9. **Paths are indicative.** Module paths under "Owns" follow the layout that T3 and T7 create. A lane maps them to the real layout and reports the mapping.

## Task cards

> **Edge gotcha (found while publishing E5):** `edge/nginx.conf` is a single-file bind mount. Ansible's copy replaces the file, so the running edge keeps the old inode, and `nginx -s reload` reloads the old config. Restart the edge container after any change. ### P1-01 · Realtime platform — wave 1 · M

**Owns**
- New `crates/server/src/events/`: per-user bus, ring buffer, coalescer.
- The SSE route (T11).
- New routes `notifications`, `client_errors` and `version`.
- New `crates/core/src/notifications.rs` and its `lib.rs` line.
- Router lines; the generated client.

**Acceptance**
- `GET /api/v1/events`, one test per behavior:
  - `hello` on connect, then a 20 s comment heartbeat;
  - headers `X-Accel-Buffering: no` and `Cache-Control: no-store`; the `topics` filter;
  - a per-user `broadcast` with capacity 256;
  - `Last-Event-ID` replay from a 256-event, 5-minute ring;
  - an older gap or a lagging receiver gets `resync`.
- Typed events `posts.changed`, `stats.changed`, `job.updated` and `notification`, with the §2.10 throttles.
  - *Assumption (G1):* coalescing is leading-edge. The first change goes out at once, follow-ups are merged, and the flush comes within 2 s.
- Isolation: user A never receives user B's events.
- An in-process probe measures write → event at an SSE client: p95 ≤300 ms.
- Also: `GET /notifications` (cursor), `POST /notifications/read`, `GET /version`, and `POST /client-errors` (64 KiB default limit, no post-content fields; its rate limit comes in P1-15).
- Per-route authz tests; the client is regenerated.

### P1-07 · Job system — wave 4 · L

**Owns**
- New `crates/server/src/jobs/**`: scheduler, workers, job-kind registry.
- The control-DB jobs repository and the idempotency middleware.
- Routes `jobs` and `queues`; router lines; the generated client.

**Acceptance**
- The scheduler follows §2.12:
  - a per-kind, per-user FIFO served round-robin;
  - claims by a conditional `UPDATE`;
  - leases renewed every third of their length; an expired lease re-queues the job with `attempts + 1`;
  - delayed jobs on a timer keyed by the smallest `run_at`;
  - `running` turns back into `queued` at boot;
  - backoff with jitter, and transient vs permanent errors;
  - a `CancellationToken` per job, and `queue_state` pause and resume;
  - finished jobs pruned after 14 days;
  - a nightly schedule at 03:00 UTC, and a hook for the 10-minute drain sweeper;
  - shutdown within 25 s.
- `jobs_active_dedupe` is enforced.
- Job-creating POSTs take an `Idempotency-Key` (24 h); the same key returns the same response.
- Routes:
  - `GET /jobs` and `GET /jobs/summary`;
  - `POST /jobs/{id}/cancel` and `POST /jobs/{id}/retry`;
  - `POST /queues/{kind}/{pause,resume,cancel-all,clear-finished}`.
- `job.updated` is sent at most every 250 ms per job.
- Tests with a test clock:
  - fairness: user A has 6,000 jobs queued and user B has 1, and B runs within one round;
  - lease expiry;
  - restart recovery, with no job lost or duplicated;
  - cancel, pause, and idempotent replay;
  - per-route authz.
