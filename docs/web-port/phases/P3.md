3. **No production secrets.** Tests and local servers make a throwaway master key. No lane reads the main checkout's `.env`. Only the lead's real runs (P3-10, P3-24's real mode, P3-29) read its `SHELFY_EVAL_*` entries, through `--env-file`.
4. **The stub, not real providers.** Tests, e2e and local servers run `shelfy-ai-stub` (P3-01) as the operator provider, or as a BYOK provider through the test-only loopback setting (P3-19). CI needs no network. No provider answer, and no prompt with library content, is committed. Outputs of real runs stay in `../shelfy-web-local/ref/p3/`.
5. **The node is shared.** No lane calls the owner's node. The lead's real runs use concurrency 1 at a quiet time. "Node offline" ends a run cleanly with "retry later", never as a failure. Nothing in Shelfy wakes the node or calls Hermes.
6. **Keys in types.** Provider keys, the operator key and master-key material live in `secrecy` and `zeroize` types end to end. A task that handles a key extends the planted-secret test (as `tests/log_redaction.rs` does): logs, problem details, metrics, job payloads, notifications, SSE events and answers.
7. **One way out.** AI calls go through the AI service (P3-09) and `crates/ai`'s client. User-entered base URLs: HTTPS, public addresses only, no redirects, and the egress proxy once P4 sets it. The operator endpoints are the only exceptions, by exact scheme, host and port; tests add the loopback setting of P3-19, which a public server refuses.
8. **Content leaves only for the user's action**, and only to a consented provider. Captions and page text are wrapped as untrusted data. Media go as bytes from the CAS, never as URLs.
9. **Prompts and schemas** change only in `shared/ai/`. An output-schema change bumps `schemaVersion`. A catalog prompt change updates P3-24's digest only together with a real-run report.
10. **Paid or shared fan-out has a guard:** an estimate and a confirmation (analysis), a rate limit and a cache (suggestions), one at a time (chat, cluster and alias runs), and the operator's own limit.
11. **Golden parity.** A ported desktop AI helper gets a golden set (`scripts/golden/ai-*.ts`, one line in `run.ts`) and matches it byte for byte. Desktop exports come only from P3-03.
12. **Error codes.** A lane that adds an `ErrorCode` adds its message, in every language, to `src/i18n/messages/errors.ts`: `web/tests/errors.test.ts` reads the generated document.
13. **AI writes yield to the user.** Results go through `update_ai` inside `library::write`, guarded by the item's claim, so an edit, a clear or a trash made meanwhile wins.
14. **The AI seam.** Views use `ShelfyClient.ai` (P3-08). Each area has its interface in `src/api/ai/`, its desktop implementation in `src/api/ai/electron.ts` and its web one in `web/src/api/ai/`, and turns on with its own capability flag.

## Task cards

### P3-01 · Provider adapters and the stub provider — wave 1 · L · Opus

**Owns**
- New crate `crates/ai` (`shelfy-ai`): the HTTP client and its address guard, the OpenAI-compatible, Anthropic and whisper.cpp adapters, SSE parsing, structured output, errors and retries, presets.
- The test stub: module `shelfy_ai::stub` and binary `shelfy-ai-stub`, behind the `stub` feature.
- The workspace member line and new workspace deps (`reqwest` with rustls, `secrecy`).

**Shared registries:** crates (root `Cargo.toml`, `Cargo.lock`; `deny.toml` only if a license needs it).

**Acceptance**
- Requests: a system prompt and messages of text and WebP images; temperature, max tokens, and `reasoning_effort` when the model takes it; output as text or as JSON for a schema; streaming on or off.
- OpenAI-compatible: `{base}/chat/completions` with the base URL verbatim plus the suffix (a test uses Gemini's `…/v1beta/openai` shape), `image_url` data URLs, `/embeddings`, `/audio/transcriptions`, `/models`, and an optional `/health` probe (llama.cpp servers).
- Anthropic Messages: `{base}/v1/messages`, a top-level system prompt, base64 image blocks, forced tool use whose `input_schema` is our schema, `input_json_delta` streaming. Embeddings and STT answer `unsupported`.
- whisper.cpp: `POST {url}` (the `/inference` endpoint) with multipart `file` (16 kHz mono WAV), `response_format=json`, `temperature=0` and `language`, as `electron/stt.ts` sends it; an optional Bearer key.
- Structured output: strict `json_schema`; else `json_object`, validated with `jsonschema`, plus one repair call that quotes the validation error; else `schema_invalid`. The mode comes from the preset or the operator config, and can be overridden per call.
- Streaming: partial text to a callback. An empty or invalid stream gets one non-streaming retry (desktop AI-13).
- Errors: `offline` (connection refused, no route, DNS failure, connect timeout), `invalid_key` (401, 403), `rate_limited` with `Retry-After`, `quota_exhausted`, `transient` (5xx, read timeouts, resets), `bad_request`, `refused`, `schema_invalid`, `unsupported`, `cancelled`.
  - Up to 3 retries with jitter on transient and rate-limited errors, honoring `Retry-After` up to a cap. None on `offline` (the caller holds the work), an invalid key or an exhausted quota.
- Timeouts come from the caller, connect and total apart (cloud catalog 120 s; chat first token 20 s and 60 s in all; the operator's own, P3-09).
- The client: rustls; redirects off.
  - For user-entered base URLs: HTTPS only, and a resolver that refuses loopback, private, link-local (169.254.169.254 included), CGNAT 100.64/10, unique-local, multicast and reserved addresses, IPv4-mapped and NAT64 forms, and any answer set that holds one. `SHELFY_EGRESS_PROXY`, when set, carries every such call (P4 sets it).
  - An exact allowlist of `scheme://host:port` endpoints, given by the server (the operator provider, P3-09), passes the guard, may use http, and connects directly, never through the proxy.
  - Tests: decimal, octal and hex IPv4 literals; `[::ffff:127.0.0.1]`; a test resolver that answers a private address; a 302 that is not followed; a user URL with the allowlisted host but another port or scheme is refused.
- Keys are `secrecy::SecretString`. A test plants a key and finds it in no `Debug` or `Display` of requests, endpoints or errors.
- Answers carry token usage (from `usage` when the server sends it, else none) and timings. The crate records no metric (P3-09 does).
- The stub provider:
  - OpenAI-compatible, Anthropic and whisper.cpp endpoints plus `/health`, with deterministic schema-valid answers, canned answers keyed by a hash of the request text, or replay from a recordings directory;
  - fault injection (offline: refused connections; 429 with `Retry-After`; 500; timeout; slow first token; 401; malformed JSON; non-conforming JSON; empty stream) and latency injection (for P5's §6.3 scenario C);
  - a request log without keys, for assertions.
- Presets: OpenAI, Anthropic, Gemini (OpenAI-compatible), OpenRouter, Groq, Mistral, Together and Custom. Each has a kind, a base URL, the tasks it serves (vision, embeddings, STT) and a provisional structured-output mode, all "unverified" until SPIKE-6's cloud rows.
- Every path above has a test against the stub; a proptest covers the SSE parser.

**Assumptions**
- *(G3-2)* AI calls use this client, separate from P2's outbound client. Both honor `SHELFY_EGRESS_PROXY`.
- `crates/ai` depends on no workspace crate, so P6 can reuse it in the desktop.
- *(G3-23)* No model id is a hard-coded default.

### P3-02 · Key vault and the master key — wave 1 · M · Opus

**Owns**
- New `crates/server/src/ai/mod.rs` and `crates/server/src/ai/vault.rs`; new `crates/server/src/control/provider_keys.rs`.
- New `crates/server/src/admin/rekey.rs`.
- `SHELFY_MASTER_KEY` and `SHELFY_MASTER_KEY_PREVIOUS` in `crates/server/src/config.rs`, with their `deploy/README.md` rows.
- Workspace deps `chacha20poly1305`, `hkdf`, `zeroize` (and `secrecy`, if P3-01 has not landed).

**Shared registries:** crates (server `lib.rs`, Cargo), admin, config, state.

**Acceptance**
- Config:
  - each variable is base64 of exactly 32 bytes; anything else stops the start, with a message that never echoes the value;
  - empty means unset. Without `SHELFY_MASTER_KEY` the vault is off: BYOK keys cannot be stored, and the operator provider still works.
- Keys: per user, HKDF-SHA256 from the master key (salt: a fixed domain label; info: `provider-keys` and the user id). `key_version` is a 32-bit id derived from the master key with another info, so a row names its master key without storing it.
- Sealing: XChaCha20-Poly1305, a random 192-bit nonce per seal, and AAD = user id, provider id and `key_version`.
  - Tests: a row opened for another user or provider fails; a changed ciphertext, nonce or AAD fails.
- `provider_keys` rows (control v1, no migration): nonce, ciphertext, `last4`, `key_version`, `created_at`. `last_used_at` is written at most once a minute.
- Rotation:
  - `SHELFY_MASTER_KEY_PREVIOUS` opens rows of the old version;
  - `admin rekey [--dry-run]` re-seals every row under the current key. It is idempotent and resumable, and prints counts only;
  - a test rotates, rekeys, unsets the previous key, and reads every row.
- Hygiene:
  - plaintext keys only in `SecretString`, derived keys in `Zeroizing`; no `Debug`, `Display` or `Serialize` shows a key;
  - a test plants a provider key and a master key, and finds neither in the logs (tracing capture), problem details, `Debug` of the config and the state, or `/metrics`.
- The start log states the vault's state and the current `key_version`, never a key.
- `admin snapshot` output holds sealed rows only (test).

**Assumptions**
- *(G3-4)* Rotation through a previous-key variable and `admin rekey` (§3.4).
- The routes that store keys are P3-19's. The operator key never enters the vault.

- `POST /ai/analyze {selector, mode: missing|selected|all, deep}`:
  - the first call returns counts (analyzable, waiting for media, already queued), an estimate and a confirmation token valid for 10 minutes;
  - the estimate gives input and output tokens per §2.15, a cost for a priced BYOK route, and for the operator provider an ETA from its measured pace;
  - the second call, with the token and an `Idempotency-Key`, enqueues; a single post enqueues on the first call;
  - new error code `confirm_token_invalid`.
- `GET /ai/queue?state&cursor`: items and counts, with an ETA from recent durations, and the provider's state (an offline node shows as waiting).
- *(G3-6)* `POST /ai/queue/cancel` and `POST /ai/queue/retry` take keys, or all. `/queues/ai.drain/{pause,resume}` work. `cancel-all` also returns pending items, through the kind's cancel hook.
- The drain:
  - one per user (dedupe key = the kind); as many calls as the route's limit allows (the operator's 1–2, or `aiConcurrency`); a 10-minute lease renewed per item; yields when paused; re-arms at the next `ai_next_at`;
  - while the provider is `offline`, it re-arms at the next probe without spending tries; the sweep re-arms users with due pending items;
  - at start, `analyzing` rows of a dead try go back to `pending`, or to `error` (`interrupted`) after 3 tries.
- Errors:
  - transient → backoff, 3 tries per item, `Retry-After` honored;
  - `schema_invalid` after the repair, `refused`, `media_unreadable` → `error`;
  - an invalid key or an exhausted quota pauses the queue instead of failing items; an open breaker holds the drain without spending tries.
- *(G3-7)* `ai.stream {postKey, text}` at most 4 Hz per item, only to streams that asked for the topic, and never in the replay ring.
- The notification `ai.analysis_finished {done, errors}` when a queue empties.
- `admin ai-status --user <id>` prints counts per state, the age of the oldest due pending item, items waiting for an offline provider, `analyzing` rows without a live drain, and errors by code. Aggregates only.
- Tests with the stub and a test clock:
  - a 500-post run with faults injected, and the provider offline for a while in the middle, ends with every item `done` or `error`, none stuck, and no try spent while offline;
  - a restart midway; pause and resume; cancel; retry; two users served in turn;
  - the guarded apply; per-route authz; no caption or prompt in the logs.
