## P4 lane rules

These add to the lane rules in EXECUTION.md and P1.md. P1 rules 1–3 (ports, generated artifacts, owned registries) are replaced by rules 1–3 below; P1 rules 4–9 apply.

1. **Ports, data, containers.**
   - Task P4-k runs its API on port `18480 + k`, with data in `../shelfy-web-local/data/p4-<k>`.
   - Its other local services (capture, egress, fixture origins, resolver) use ports `28480 + 10k` to `28489 + 10k`.
   - Docker Compose runs with the project name `shelfy-p4-<k>`. At the end, remove the lane's containers, volumes and images (`down -v`, `docker image rm`); the capture image is about 600 MB.
2. **Shared registries.** Concurrent lanes may touch them. The later lane rebases, unions the additions, takes the next free migration number, and regenerates generated files with the tools (`UPDATE_OPENAPI=1 cargo test -p shelfy-server --test openapi`, then `scripts/api-client/generate.ts`; `scripts/golden/run.ts`). Each card lists the registries it touches:
   - the plan's: router composition and route lists; job kinds; admin dispatch; library or control migrations with their schema fixtures; a crate's `lib.rs`, `Cargo.toml`, `Cargo.lock`; `openapi.json` and the TS client; `ci.yml`; root `package.json` or `pnpm-lock.yaml`; `src/App.tsx`, the nav (Sidebar, BottomNav), the i18n messages;
   - P4 adds: `ErrorCode` and `src/i18n/messages/errors.ts`; `events/model.rs`; `config.rs` with its `deploy/README.md` rows; the maintenance loop in `serve.rs`; the server `Capabilities` and the client `ShelfyCapabilities`; the seam interfaces; `useSections`; `deploy/compose.test.yml`; `release-server.yml`; the golden `SETS`.
3. **Late needs.** A need marked *(late)* is needed only for the task's last step: route wiring, CI or UI wiring. The lane may start before it is integrated, and rebases onto it.
4. **Untrusted output.** Treat as untrusted everything that comes from the capture service, uploads, imports and fetched URLs:
   - check the schema, cap the sizes, sniff the types;
   - no file name from such a source reaches the file system unchecked, and no symlink is followed;
   - a test plants a hostile input for every path that reads one.
5. **Egress.** Every outbound request of the API goes through P4-01's client. Tests use its `direct` mode, which works only with a loopback public URL.
6. **Quota.** Every writer that stores bytes calls `quota::reserve` (P4-07) before writing and commits afterwards.
7. **No real third-party network in tests or CI:** use fixture origins, fake binaries and a local Smokescreen. Real sites appear only in the lead's VPS runs and in the local desktop baseline (P4-27, P4-31).
8. **Desktop files.**
   - Only P4-03 edits `electron/webcap/*`, `electron/webcapture-playwright.ts` and `electron/weborchestrator.ts`.
   - UI tasks edit the `src/` files they list (P1 rule 5).
   - Desktop checks, `pnpm test:e2e` and `pnpm eval:capture` stay green.
9. **Spike inputs.** If the SPIKE-4, SPIKE-9 or SPIKE-11 note is not on `web/foundations` when a lane starts, the lane uses the plan's values, marks each one "pending SPIKE-n" in code comments and in its report, and the lead re-checks them at integration.
10. **Codes, not prose.** Every new problem, stage, capture event and job error is a stable `snake_case` code, with an Italian and an English string. The server never sends UI text (§2.9).
11. **Privacy.** VPS and baseline reports give aggregates only: no URL, title or caption of the owner's posts. The six public audit sites, already named in `docs/website-analyzer-audit.md`, may be named.

## Task cards

> **Untrusted-output gotcha.** The capture container runs arbitrary web pages, so assume a Chromium exploit can control it. It shares `/data/shelfy/work/capture` with the API and talks to the API only through its response stream. A symlink it plants in that directory resolves inside the API's mount, where every user's library lives. P4-14 opens artifacts with `O_NOFOLLOW` and P4-13 refuses requests from the capture subnet.

### P4-01 · Egress client — wave 1 · S · Opus

**Owns**
- New `crates/server/src/egress.rs`: the only place that builds an outbound HTTP client.
- `crates/server/src/config.rs`: `SHELFY_EGRESS_PROXY`.
- New `crates/server/tests/egress.rs`.

**Registries:**
- server `lib.rs`;
- server `Cargo.toml` and `Cargo.lock`: `reqwest` with rustls and streaming, no default features;
- `config.rs` and its `deploy/README.md` rows.

**Acceptance**
- `Egress::client(purpose)` returns a `reqwest` client that:
  - sends every scheme through `SHELFY_EGRESS_PROXY`;
  - keeps no cookies and does not decompress bodies on its own;
  - follows redirects by our own policy: at most 5 hops, http(s) only, ports 80 and 443 only, each hop sent through the proxy again;
  - applies per-purpose timeouts, byte caps (`read_capped`), at most 64 requests in flight, and per-host-group limiters that later tasks configure (§2.3).
- `Egress::internal()` is the only client that bypasses the proxy, and it reaches only the origin of `SHELFY_CAPTURE_URL`.
- Configuration:
  - with `SHELFY_EGRESS_PROXY` unset, outbound features are off: their capabilities are false and the problem is `egress_unavailable`;
  - the value `direct` is accepted only with a loopback `SHELFY_PUBLIC_URL`, like `SHELFY_DEV_MAILBOX`.
- A test fails when a `reqwest` client is built outside `egress.rs` in `crates/server` or `crates/media` (§3.2). The migration CLI's `ureq` is exempt: it runs on the user's machine.
- Tests against a proxy stub:
  - the proxy sees every request, redirect hops included;
  - a redirect to `file:`, to another port or past the 5th hop is refused;
  - a capped body stops at the cap.
- Metric `shelfy_egress_requests_total{purpose,outcome}`, with no per-user label.

**Assumptions**
- The proxy resolves names and checks IPs (D17); the client adds no IP check of its own.
- P2's archive worker and P3's provider calls build on this client (cross-phase; proposed owner P4).

### P4-03 · Capture service on capture v2 — wave 1 · L · Opus

**Owns**
- New `capture/`:
  - `capture/src/server.ts`: `node:http` and zod;
  - `capture/src/env.ts`: paths, limits, the proxy, the ffmpeg path, the adblock engine;
  - `capture/src/electron-shim.ts`: the build alias for `electron`;
  - `capture/src/run.ts`: one site;
  - `capture/src/protocol.ts`, with the generated contract `capture/protocol.schema.json`;
  - `capture/src/fake.ts`: replays a recorded capture;
  - `capture/build.ts` (esbuild), `capture/tests/**`, `capture/fixtures/recorded/**`;
  - `tsconfig.capture.json`.
- New `shared/capture/codes.json`: the event, stage and failure codes, the contract with the SPA.
- Desktop edits (P4 rule 8):
  - `electron/webcap/{capture,driver,blocker,encode}.ts`: codes, plus injectable paths, fallback and page concurrency;
  - `electron/webcapture-playwright.ts`: injectable launch options;
  - new `electron/webcap/assemble.ts`: the pure site assembly, extracted from `electron/weborchestrator.ts`, which now calls it.

**Registries:** root `package.json` and `pnpm-lock.yaml` (`zod`; the scripts `capture:build` and `typecheck` gain `tsconfig.capture.json`); `vitest.config.ts`.

**Acceptance**
- `POST /v1/captures`:
  - checks `X-Shelfy-Internal-Token` in constant time (401 otherwise);
  - validates the body with zod: `captureId` (a ULID), `url` (http(s), at most 2,048 characters), `maxPages` (1–8), `singlePage`, `video`, and `workDir`, which must equal `/work/<captureId>`;
  - answers 503 `busy` without a free slot.
- The response is §2.18's NDJSON:
  - `event` lines carry `kind`, `code` and `params`, never prose;
  - `page` lines name asset files relative to the work dir;
  - the stream ends with `done` (`manifest`, `durationMs`, `peakRssBytes`, `bytes`) or `failed` with a code: `capture_blocked`, `timeout`, `navigation`, `empty` or `internal`;
  - lines are at most 256 KiB, and a capture sends at most 250 events.
- `manifest.json` is written before `done`. It holds the site assembly, with no file paths:
  - title, site name, description, languages;
  - palette, typography, tech, awards, traits, digests and `webMeta`;
  - pages with their assets (role, seq, CSS top and height) and the hero, og image, favicon, video and poster;
  - engine, user agent and viewport;
  - skipped pages with reason codes, QC verdicts, and the timeline (at most 250 codes).
- Closing the response aborts the capture within 5 s: pages, browser contexts and ffmpeg are killed. The API deletes the work dir.
- `GET /health` answers `{ok, slotsFree, browser, version}`.
- Network:
  - every Node fetch (discovery, sitemaps, og image, favicon) goes through `CAPTURE_PROXY`;
  - Chromium starts with `--proxy-server` and `--disable-quic`, resolves no names locally, and is sandboxed as SPIKE-4 decides;
  - service workers are blocked; downloads, dialogs and popups are refused; no cookies are imported;
  - a test proves the Electron fallbacks (`electron-driver.ts`, `system-chrome.ts`) cannot run in the service.
- Budgets (§2.18; SPIKE-11's values when present):
  - 1 site at a time, 2 pages in parallel, 1 when the site is WebGL-heavy or scroll-jacked;
  - 150 s per page and 10 min per site;
  - at most 80 MB of artifacts per site: further pages are skipped as `budget_exceeded`;
  - pages at most 30,000 CSS px tall;
  - ffmpeg with `-threads 1`; the browser closes after 120 s idle.
- Parity: for a recorded fixture capture, the desktop's `captureWebReference` and the service produce the same assembly, through `assemble.ts` (vitest).
- `capture/src/fake.ts` replays a recorded fixture capture, stream and artifacts, for the API and web e2e tests.

  1. a kept or cached video: serve it;
  2. `post_media.video_url`, present, with at least 5 minutes left, on the platform's video CDN hosts: fetch it through P4-01;
  3. if the SPA reports the extension (`extension: true`) and P2's task queue exists: queue a `refresh_media` task for the post, wait with requeues every 30 s for at most 30 min (stage `awaiting_extension`), then fetch the fresh URL (PG11);

  - files `cache/video/<user>/<sha256>.mp4`;

  - one global LRU at `SHELFY_VIDEO_CACHE_GB` (default 5), trimmed on insert and hourly, least recently served first;

- Keeping a video (`keep: true`, or keeping a cached one):

  - moves the file from the cache into the user's CAS (`role=video`, `origin=server`);
  - sets `post_media.video_object_id` and drops the cache row;
  - announces `posts.changed`.
- Bulk `fetchMedia {what: "video", keep}` over the selector:
  - at most 200 posts per request (Q3);

  - one `media.video` job per post.

- Tests, with P4-06's fake binaries and a loopback origin (`direct` egress):
